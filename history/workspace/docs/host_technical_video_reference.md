# ESP32-P4 上位机 Host 技术展示文档

本文用于队友拍摄作品视频和比赛答辩准备。重点不是把上位机描述成“电脑显示界面”，而是展示它在整套视觉分拣系统中的工程价值：稳定通信、实时监控、图像记录、链路诊断和控制下发。

## 1. 一句话定位

Host 是基于 Qt 6 的跨平台桌面上位机，用于连接 ESP32-P4 视觉分拣板，实时接收板端遥测、检测图像和分拣状态，并提供现场控制、数据留存和链路维护能力。

它的定位是“边缘设备的数据中心和控制台”：

- 板端负责相机采集、视觉识别、分拣调度和电机控制。
- 上位机负责以太网通信、图像显示、性能监控、包裹记录、日志保存和人工控制入口。
- 系统采用边缘计算架构，推理留在 ESP32-P4 端完成，减少对电脑环境和本地模型服务的依赖。

## 2. 系统架构

### 2.1 硬件与网络角色

| 角色 | 地址/端口 | 作用 |
| --- | --- | --- |
| PC 上位机 | `192.168.10.1/24` | 监听 TCP 服务，接收板端连接 |
| ESP32-P4 板端 | `192.168.10.2` | 主动连接上位机，上传数据和接收控制 |
| 控制链路 | `5000/tcp` | 遥测、控制、时间同步、分拣 SIM line 协议 |
| 图像链路 | `5001/tcp` | JPEG/RGB 图像数据传输 |

板端主动连接 PC，上位机只需要固定网卡 IP 并打开监听端口。现场部署时，队友可以拍摄网线连接、PC 网卡 IP、上位机“设备在线”状态和两个端口说明页。

### 2.2 软件分层

当前 host 工程位于 `esp32_host_no_inference`，主要分层如下：

| 层级 | 关键模块 | 作用 |
| --- | --- | --- |
| UI 层 | QML 页面 | 性能总览、视觉检测、设备控制、系统维护 |
| 状态适配层 | `HostController` | 向 QML 暴露状态、图像 URL、遥测指标、控制接口 |
| 网络工作层 | `HostNetworkWorker` | 独立线程监听 control/image 两路 TCP，负责收包和初步分发 |
| 协议层 | `packetprotocol` | 解析自定义二进制包头，生成下行 packet |
| 本地数据层 | Documents/ESP32Host | 保存图片、遥测 JSONL 和运行记录 |

数据流可以这样讲：

```text
ESP32-P4
  -> TCP control/image 双链路
  -> HostNetworkWorker 独立网络线程
  -> PacketProtocol 拆包和校验
  -> HostController 转换为 UI 状态
  -> QML 实时展示 + 本地文件归档
```

这个结构把 UI、通信、协议和数据处理拆开，避免 QML 直接处理 socket，也方便以后扩展串口、UDP 或新的协议版本。

## 3. 核心技术亮点

### 3.1 双 TCP 链路设计

上位机不是把所有数据塞进一个连接，而是拆成两条链路：

- `5000/tcp` 控制链路：处理遥测 JSON、检测 JSON、时间同步和控制命令。
- `5001/tcp` 图像链路：处理大体积 JPEG/RGB 图像包。

这样做的好处：

- 图像包体积大，不会阻塞控制和状态消息。
- 控制链路可以保持低延迟，方便电机速度、时间同步等命令及时到达。
- 视频展示时，可以把它讲成“数据面”和“控制面”分离，体现工程架构设计。

当前实现中，上位机优先绑定 `192.168.10.1`，如果绑定失败会 fallback 到 `AnyIPv4`，提高现场演示容错性。socket 启用 `LowDelayOption`，图像链路配置了更大的读缓冲：Qt read buffer 为 4 MiB，系统接收缓冲为 1 MiB，适合连续接收 JPEG 图像。

### 3.2 独立网络线程

网络收包运行在 `HostNetworkWorker`，并被移动到独立 `QThread`。

这个设计解决两个问题：

- 图像数据接收、TCP 粘包拆包、JSON 解析通知不会卡住 UI 主线程。
- UI 动画、趋势图、图像切换仍然可以保持流畅，比赛演示时不容易出现“界面假死”。

QML 页面只绑定 `HostController` 暴露的属性，例如 `connected`、`latestImageUrl`、`dashboardCards`、`frameHistory`、`metricHistory`。这属于典型的 Qt 工程分层：后台线程负责 I/O，前台线程负责展示。

### 3.3 自定义二进制 Packet 协议

Host 使用固定 40 字节包头，而不是直接发送裸 JSON 或裸图片。包头包含：

| 字段 | 作用 |
| --- | --- |
| magic | 固定为 `"ESP2"` little-endian，用于识别协议包 |
| version | 当前版本 `1` |
| type | 包类型，例如图像、遥测、检测、时间同步 |
| seq | 包序号，用于追踪帧和调试顺序 |
| timestampMs | 发送时刻，便于估算延迟 |
| payloadLen | 负载长度，用于 TCP 流中拆包 |
| width/height | 图像宽高 |
| pixelFormat | 图像格式，支持 RGB888 和 JPEG |
| reserved/reserved2 | 当前用于携带分类 ID 和置信度 |

协议包类型：

| Type | 含义 |
| --- | --- |
| `0x01` | 图像包 |
| `0x02` | 遥测 JSON |
| `0x03` | 检测 JSON |
| `0x10` | 时间同步 JSON |
| `0x11` | 控制 JSON |
| `0x12` | 分拣 SIM line / CONFIG 命令 |

协议解析具备基础鲁棒性：

- 最大 payload 为 8 MiB，异常长度会被丢弃。
- 如果 magic/version/header size 不匹配，会按字节滑动重同步，适合处理 TCP 流错位。
- 对图像 payload 做格式校验：RGB888 校验字节数，JPEG 校验起始标记。

答辩时可以强调：TCP 是字节流，没有天然消息边界，因此自定义 packet header 是为了稳定拆包、识别帧、承载图像元数据和后续扩展。

### 3.4 图像接收、增强与归档

上位机支持两种图像格式：

- RGB888：按宽高计算期望字节数。
- JPEG：检查 JPEG 起始标记，并直接解码显示。

接收后，Host 会进行以下处理：

1. 解码图像。
2. 修正红蓝通道顺序，适配板端图像编码链路。
3. 做轻量预览增强，包括中值降噪和轻微锐化。
4. 重新编码为 JPEG。
5. 原子写入本地文件，避免写一半时 UI 读到坏图。

保存路径在用户 Documents 目录下：

```text
Documents/ESP32Host/images/frame_000001.jpg
Documents/ESP32Host/images/latest_preview.jpg
```

每个包裹都会进入历史记录，包含包裹编号、分类、置信度、分辨率、接收时间和图片路径。视频可以拍“视觉检测”页，展示最新图像和右侧包裹图像记录，说明系统不仅能实时看，还能赛后追溯。

### 3.5 板端性能遥测与趋势图

Host 接收板端上传的遥测 JSON，并将其转换为 dashboard 指标：

- CPU 总占用、CPU0/CPU1 占用。
- PSRAM 使用率和剩余容量。
- heap/internal memory 使用情况。
- 最大空闲块，用于观察内存碎片。
- FPS、链路延迟、运行时长。
- 图像编码/发送耗时和最近 JPEG 体积。

上位机会维护短时历史队列，并用 QML Canvas 绘制趋势图。评委看到的不是静态界面，而是实时变化的系统运行状态。

遥测原始数据会追加保存为：

```text
Documents/ESP32Host/telemetry.jsonl
```

JSONL 的好处是每一行都是一条独立记录，后续可以用脚本分析比赛现场运行状态，例如内存是否下降、图像发送是否丢包、FPS 是否波动。

### 3.6 图像链路健康监控

系统维护页和 dashboard 中展示图像链路健康指标：

- 已编码 / 已发送图片数量。
- 当前图像队列深度。
- 背压丢弃次数。
- 过期丢弃次数。
- 无可用快照次数。
- 最近一次 JPEG 大小。
- 最近编码耗时和发送耗时。

这些指标可以说明系统不仅“能跑”，还具备工程诊断能力。比赛现场如果出现网络或处理压力，上位机能帮助定位是图像编码慢、发送慢、队列堆积，还是板端没有可用快照。

### 3.7 控制命令下发与节流

上位机支持时间同步和电机速度下发。

时间同步通过 JSON packet 发送：

- `unix_ms`：当前毫秒时间戳。
- `tz_offset_min`：本地时区偏移。

电机速度通过分拣 SIM line 发送：

```text
CONFIG a_speed=<v> b_speed=<v> c_speed=<v>
```

其中 `<v>` 为 0 到 100 的速度百分比。当前 UI 的“电机转速”滑块会同时设置 A/B/C 三路速度。

控制链路做了两个工程处理：

- 去重：相同值不会重复发送。
- 100 ms 节流：滑块连续拖动时，不会把大量命令瞬间刷到板端。

这能体现上位机不是单纯 UI，而是考虑了现场控制稳定性的工程工具。

### 3.8 跨平台部署能力

Host 使用 Qt 6 Quick + Qt Network + C++17，构建系统是 CMake。当前目标是兼容 Windows 和 Linux：

- Linux 可以直接用系统 Qt 运行。
- Windows install 流程使用 Qt deployment，复制 DLL、plugins 和 QML imports。
- 项目没有绑定 MSVC 或 MinGW，保持 Qt Desktop kit 可移植性。

比赛展示时可以说：上位机不依赖单一开发机，可以部署到 Windows 笔记本或 Linux 工控环境。

## 5. 60 秒答辩讲解词

这套系统的上位机使用 Qt 6 和 C++ 实现，主要负责 ESP32-P4 视觉分拣板的数据接入、实时监控和控制。板端完成相机采集、视觉识别和电机分拣，上位机通过以太网接收结果。

通信上，我们使用了双 TCP 链路：`5000` 端口负责遥测、控制、时间同步，`5001` 端口专门负责 JPEG 图像。这样图像大数据不会阻塞控制命令。协议层使用固定 40 字节二进制包头，包含包类型、序号、时间戳、payload 长度、图像宽高和分类置信度，可以稳定处理 TCP 粘包和半包。

上位机内部把网络 worker 放到独立线程，UI 只绑定控制器暴露的状态，所以实时收图和拆包不会卡住界面。收到图像后会解码、通道修正、预览增强并保存到本地；遥测数据会显示 CPU、PSRAM、heap、FPS、图像队列和丢包情况，还会保存成 JSONL，方便赛后分析。

因此这个上位机不仅是显示界面，它同时承担通信网关、运行监控、图像归档和现场控制台的作用。

## 6. 2 分钟答辩讲解词

我们的上位机是整套 ESP32-P4 视觉分拣系统的 host 控制台，使用 Qt 6 Quick、C++17 和 Qt Network 开发，可以在 Windows 和 Linux 上部署。系统分工上，板端负责边缘视觉推理和分拣执行，上位机负责把板端的图像、分类结果、性能状态和控制入口集中展示出来。

通信设计上，我们没有使用单一 socket 混传所有数据，而是拆成两条 TCP 链路。`5000/tcp` 是控制链路，负责遥测 JSON、检测 JSON、时间同步和控制命令；`5001/tcp` 是图像链路，专门接收 JPEG 或 RGB888 图像。这样图像传输压力不会影响控制命令的实时性。图像 socket 还配置了更大的接收缓冲，并开启低延迟选项，适合现场连续收图。

协议层是自定义二进制 packet。每个包都有固定 40 字节 header，包括 magic、version、type、seq、timestamp、payloadLen、图像宽高、像素格式和保留字段。由于 TCP 本身是字节流，没有消息边界，这个 header 可以让上位机稳定拆包、处理粘包半包，并通过 seq 和 timestamp 做调试追踪。异常 payload 会被丢弃，header 错位时会滑动重同步。

软件架构上，`HostNetworkWorker` 运行在独立 `QThread`，负责监听、收包和协议分发；`HostController` 把网络数据转换为 QML 可绑定的属性；QML 只负责展示性能总览、视觉检测、设备控制和系统维护页面。这样网络 I/O 不会阻塞 UI，也让通信逻辑和界面逻辑解耦。

数据处理方面，收到图像后，上位机会完成解码、红蓝通道修正、轻量降噪锐化和本地 JPEG 保存。每个包裹都有历史记录，可以查看类别、置信度、分辨率和图片。遥测数据会显示 CPU、PSRAM、heap、内部内存、最大空闲块、FPS、图像队列、背压丢弃和编码发送耗时，并保存为 `telemetry.jsonl`，方便赛后分析。

控制方面，上位机可以同步板端时间，也可以通过 `CONFIG a_speed b_speed c_speed` 命令调整三路电机速度。滑块控制做了去重和 100 ms 节流，避免连续拖动时控制链路被刷爆。

所以这个 host 的技术亮点是：双链路实时通信、自定义可靠拆包协议、独立网络线程、图像归档、遥测诊断和控制闭环。它让评委不仅能看到识别结果，还能看到系统运行是否稳定、链路是否健康、数据是否可追溯。

## 7. 评委可能追问

### 为什么要分成两个 TCP 端口？

图像数据体积大，控制和遥测数据体积小但更需要低延迟。拆成 control 和 image 两条链路后，即使图像包比较大，也不容易影响控制命令、时间同步和运行状态更新。

### 为什么上位机不做本地推理？

这是边缘计算设计。识别和分拣决策在 ESP32-P4 板端完成，上位机负责展示和记录。这样现场运行不依赖电脑 GPU、本地模型服务或 Python 环境，系统更接近真实嵌入式部署。

### TCP 粘包和半包怎么处理？

每个数据包都有固定 40 字节 header，里面包含 payload 长度。上位机先在缓冲区里解析 header，再等待完整 payload 到达后处理。如果 header 不合法，会向后滑动一个字节重新寻找 magic，实现重同步。

### 如果图像链路压力变大怎么办？

上位机会显示图像队列深度、背压丢弃、过期丢弃、编码耗时、发送耗时和最近 JPEG 大小。这些指标可以帮助判断瓶颈在编码、发送还是网络接收。

### 数据会不会只显示不保存？

不会。图像会保存到用户 Documents 下的 `ESP32Host/images`，遥测会追加到 `telemetry.jsonl`。视频结束后仍然可以查看历史图像和运行数据。

### 上位机如何保证 UI 不被网络收包卡住？

网络层运行在独立 `QThread` 中，QML UI 只绑定 `HostController` 的属性。收包、拆包和初步分发不在 UI 主线程执行。

### 目前哪些控制是真实下发的？

时间同步和电机速度是真实通过控制链路下发的。电机速度会发送 `CONFIG a_speed=<v> b_speed=<v> c_speed=<v>`。亮度、检测开关、预览叠加框和置信度阈值当前主要用于上位机本地显示和展示辅助，不应在答辩中夸大成完整板端控制。

## 8. 术语表

| 术语 | 解释 |
| --- | --- |
| Host / 上位机 | PC 端控制和监控软件 |
| 板端 / 下位机 | ESP32-P4 嵌入式设备 |
| TCP | 面向连接的可靠传输协议 |
| Control Link | 控制、遥测、时间同步等小数据链路 |
| Image Link | 专门传输图像的大数据链路 |
| Packet Header | 每个协议包前面的固定长度元数据 |
| Payload | Header 后面的真实数据，例如 JSON 或 JPEG |
| QThread | Qt 的线程机制，用于把网络 I/O 从 UI 主线程分离 |
| JSONL | 每行一个 JSON 对象的日志格式，适合追加写入和后续分析 |
| Backpressure | 下游处理不过来导致队列积压或主动丢弃 |
| PSRAM | ESP32-P4 外部 RAM，用于图像、缓冲和较大数据 |
| RGB888 | 每个像素 3 字节，分别表示红绿蓝 |
| JPEG | 压缩图像格式，适合网络传输和本地保存 |

## 9. 拍摄重点总结

队友拍视频时建议围绕这句话组织镜头：

> 上位机通过双 TCP 链路接入 ESP32-P4，把板端视觉分拣过程实时可视化，同时记录图像、监控性能、诊断链路并下发控制命令。

最值得展示的画面：

1. 设备在线和双端口监听。
2. 实时 JPEG 图像进入视觉检测页。
3. 包裹历史记录不断增加。
4. CPU、PSRAM、heap、FPS 趋势实时变化。
5. 图像链路健康指标显示队列、丢弃和耗时。
6. 电机速度滑块下发 `CONFIG` 命令。
7. 系统维护页展示保存目录和运行日志。
