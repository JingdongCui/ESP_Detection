# 零拷贝 peek 防竞态：概率保证的风险说明

> 适用范围：`components/vision` 复刻 ESP-who 的"fetch ringbuf + 零拷贝 peek"帧来源机制
> 编写日期：2026-06-27
> 状态：已选用「概率保证」方案复刻，风险已知并接受，记录在此备查

---

## 一、这份文档在说什么

我们复刻 ESP-who 的推理帧来源时，选了它原生的**零拷贝 peek** 模式：
推理任务不持有帧副本，而是直接读 fetch 任务 ringbuf 里的 V4L2 帧指针（指向 mmap 区域）。

这个模式**不用读写锁保护正在读的帧**，而是靠"缓冲足够深，推理来得及在帧被回收前读完"
来避免竞态。这是一种**概率保证（probabilistic guarantee）**，不是**严格保证（strict guarantee）**。

ESP-who 官方就是这么做的，我们 1:1 照搬。本文档把这个选择的风险讲清楚，
便于将来出问题时第一时间定位，也便于决定何时升级到严格锁方案。

---

## 二、机制回顾（风险的来源）

### 2.1 帧的生命周期

```
fetch 任务（生产者）:
  VIDIOC_DQBUF 取帧            → 拿到 mmap 指针（驱动已填好数据，该缓冲“出队”不会被重填）
  push 进 ringbuf 持有          → 该缓冲一直处于出队状态，驱动碰不到它
  ringbuf 满 → pop 最旧帧       → 对该帧 VIDIOC_QBUF 还给驱动
  还回去后，驱动可随时把它重填为新一帧 ★风险起点★
```

关键点：**被 ringbuf 持有 = 安全（驱动不动）；一旦 pop 并 QBUF 还回 = 驱动随时可能覆写。**

### 2.2 读写双方访问的帧位置不同

- **推理 peek `back()`**：ringbuf 里**最新**那一帧（刚 push 进来的）。
- **fetch pop `front()`**：ringbuf 里**最旧**那一帧（最早 push 的），还给驱动。

正常情况下两者隔着整个 ringbuf 深度。深度 = `fb_count - 2`，当前 `fb_count=5`，深度 = **3**。
也就是说，推理正在读的"最新帧"，要被连续 push 进 **3** 个更新的帧之后，才会沦为
`front()` 被 pop 还给驱动。

### 2.3 为什么不加锁

ESP-who 的 `cam_fb_peek()` 只在取指针的瞬间持 mutex，**返回指针后立即释放**
（`who_frame_cap_node.cpp:53-76`）。推理拿着这个裸指针读图、跑模型，全程**无锁**。
fetch 的 pop/QBUF 也**不检查这帧是否有人在读**（`who_frame_cap_node.cpp:167-174`）。

所以两边没有任何互斥——安全完全建立在"深度够，时间来得及"上。

## 三、风险窗口：什么情况下会出问题

竞态发生的充要条件：

> **推理读某一帧的耗时，长到该帧在 ringbuf 里从"最新"被挤成"最旧"并被 pop 还给驱动，
> 且驱动恰好重填了它——而推理还没读完。**

量化一下（当前 `fb_count=5`，深度 3）：

- 推理 peek 到第 N 帧。
- fetch 每来一新帧就 push 一次；第 N 帧要被 push 进 N+1、N+2、N+3 三帧后才变成 `front()`。
- 第 N+3 帧 push 时触发"满→pop"，pop 的是第 N 帧 → QBUF 还驱动。
- 驱动拿到后可能立刻 DMA 重填。
- **若此刻推理还在读第 N 帧 → 数据被覆写 → 撕裂/花屏/喂给模型的是半新半旧的图。**

换算成时间：设采集帧率 `F` fps（帧间隔 `1/F`）。第 N 帧从被 peek 到被 pop，
中间要等 **3** 个新帧到达，即约 `3/F` 秒。

- 若 `F = 30`，安全窗口 ≈ **100ms**。推理单帧只要 < 100ms 读完图（注意：是"读完图"不是"跑完模型"——
  模型若先把图预处理/拷进自己的输入张量，真正裸读 mmap 的时间远小于推理总时长）就安全。
- 若推理预处理阶段直接在 mmap 指针上算（不先拷贝），那"裸读时长" = 预处理时长，需 < 100ms。

## 四、当前参数下的安全裕度

| 参数 | 值 | 含义 |
|------|----|----|
| `fb_count` | 5（可配宏） | V4L2 缓冲总数 |
| ringbuf 深度 | 3 | = `fb_count - 2`，推理帧被回收前的缓冲距离 |
| 留给驱动 | 2 | 1 个正在 DMA 写、1 个排队待命 |
| 采集帧率 | ~30fps（实测为准） | 决定时间窗口 |
| 安全窗口 | ~100ms @30fps | 推理裸读 mmap 的时长上限 |

**结论：只要推理在"把图读出来/预处理完"这一步控制在 ~100ms 内，当前参数安全。**
ESP-who 的检测模型预处理（PPA 或软件 resize）远快于此，所以它默认就够用。

裕度不足时的调节手段（按优先级）：

1. **加大 `fb_count`**（改宏即可）：深度 = `fb_count-2` 线性增大，时间窗口 = `(fb_count-2)/F`。
   代价：每加 1 个缓冲多占 `w×h×2` 字节 PSRAM（640×480 约 0.6MB/缓冲）。
2. **推理先拷贝再处理**：peek 后第一时间把 mmap 数据拷进推理自己的 buffer，
   之后的耗时与 ringbuf 无关。代价：一次全图拷贝（但可用 async memcpy，开销藏在 DMA 里）。
   —— 这其实就退回了"拷副本"，但只在推理侧拷一次，fetch/显示仍零拷贝。

## 五、触发后的症状（便于现场定位）

竞态触发**不会崩溃、不会报错**，只会数据损坏，表现为：

- **预览正常但推理结果异常**：因为显示也 peek 同一 ringbuf，但显示读得快（PPA 立即缩放走），
  撞窗口的概率远低于慢推理。所以可能出现"画面好好的，框却乱跳/误检"。
- **偶发、不可复现**：竞态是时序赛跑，负载抖动时才偶发。**越是"偶尔抽风一次"越要怀疑它。**
- **推理输入图出现撕裂**：图的上半部是第 N 帧、下半部是被重填的新帧（DMA 按行写）。
  若能 dump 推理输入图，撕裂是铁证。

定位建议：在推理 peek 到 release（或预处理完）之间打时间戳，
若发现该时长偶发逼近或超过 `(fb_count-2)/F`，基本可确认是它。

## 六、升级到严格保证的方案（本次不做，备查）

若将来推理耗时不可控、或撕裂确实发生，可升级为**严格保证**，两条路：

### 方案 A：reading 标记 + pop 跳过（轻量）

fetch pop 时检查"这帧是否正被推理读"，是则不 pop、不还驱动，改 pop 次新的或本轮不还。
推理 peek 时设 `reading_idx`，release 时清。

- 优点：仍零拷贝，只加一个索引判断和 mutex 保护。
- 缺点：推理特别慢时 ringbuf 可能"卡住"无法回收，需配合丢帧策略；逻辑比 ESP-who 原版复杂。

### 方案 B：推理侧拷贝（简单粗暴）

peek 后立刻把帧拷进推理私有 buffer（async memcpy），release ringbuf，之后只动私有副本。

- 优点：彻底消除竞态，逻辑最简单。
- 缺点：每帧一次全图拷贝（约 0.6MB@640×480）；但 DMA 异步、可与后续重叠，CPU 开销极小。
- 注意：这等于把"防竞态"从 ringbuf 深度移到了"拷贝"上，是之前双缓冲方案的精简版
  （只在推理侧拷一次，fetch 和显示仍零拷贝）。

---

## 七、本次决策记录

- **选用**：概率保证（ESP-who 原生方案），`fb_count=5`，ringbuf 深度 3，无读锁。
- **理由**：1:1 复刻 ESP-who，验证链路打通优先；当前推理预处理预计远低于 100ms 窗口。
- **接受的风险**：极端负载或推理裸读 mmap 超 ~100ms 时，可能偶发撕裂；不崩溃但结果异常。
- **回退/升级触发条件**：若 RTT 实测推理裸读时长逼近 `(fb_count-2)/F`，或现场出现偶发误检/撕裂，
  先调大 `fb_count` 宏，仍不够则上第六节方案 B。
