# 合并移植经验

本文用于交接后续类似合并任务：把已经验证过的一套能力，从一个旧工程迁移到另一个结构相近但不完全一致的新工程，例如后续要往 `teammatesproject_old` 这类工程里重做电机分拣、以太网模拟、视觉模型或传统 ROI 链路移植。

目标不是记录每一次命令的流水账，而是沉淀可复用的判断顺序、验证标准和风险边界。后续补齐另外两个对话中的内容时，优先补“为什么这样做”和“怎样判断成功”，不要只补“改了哪些文件”。

## 使用方式

开始新一轮移植前，先把目标工程、源工程和当前已成功工程并排确认：

- 源工程：提供已知能跑通的功能行为，例如电机分拣、TCP 上位机模拟、真实传感器链路、视觉级联链路。
- 当前成功工程：提供最近一次迁移后的落地做法和踩坑修正，优先级高于最早的 old project 记忆。
- 目标工程：只接受必要改动，尽量不顺手重构、不无证据升级依赖、不混入与本轮目标无关的 UI 或硬件改动。

每次移植都按三段走：

1. 先建立 baseline：源工程或当前成功工程必须能用同一套模拟器/实机流程跑通。
2. 再划边界：明确本轮迁移的是哪条链路，哪些依赖、配置、模型、UI 和硬件映射不属于本轮。
3. 最后小步验证：每一类高风险改动后都要能回到一个可解释的 build/flash/monitor/TCP audit 结果。

## 第一轮经验摘要

这次成功合并的核心经验是：不要把“功能移植”“依赖升级”“模型替换”“硬件调参”混成一个不可拆的改动。每条链路先复刻可运行行为，再用实测日志决定是否需要改变底层依赖或架构。

电机分拣链路的可迁移边界比较清楚：

- 真实硬件和以太网模拟共用调度核心，核心是 sorter scheduler 与 `sorting_sim_control`。
- TCP 模拟 20 件是有效 baseline，但它不能覆盖 GPIO 电平、传感器 active level、防抖、真实推理延迟和编码器输入。
- `CLASS1/2/3` 是物理出口语义，不一定等于模型输出类别顺序；视觉类别到物理出口要单独确认。

findlogo 视觉链路的主要教训：

- 模型文件本身、ESP-DL 版本、SPIFFS 文件名长度、输入输出张量结构、RGB/BGR 顺序都可能成为失败点。
- 只替换模型时如果启动阶段崩溃，不要默认是模型推理逻辑问题；先确认依赖版本和模型 schema 是否兼容。
- RGB/BGR 必须按整条链路记录：相机实际输出、`img_t.pix_type` 声明、`ImagePreprocessor` 目标格式、模型训练/导出期望格式，不能靠注释猜。
- 类别顺序以训练配置和模型导出事实为准。当前 findlogo 为 `0=jt`、`1=yd`、`2=zt`，但物理分拣出口保留 `JT->CLASS1`、`ZT->CLASS2`、`YD->CLASS3`。

## 后续补齐方向

另外两个对话应继续补充：

- 完整文件级迁移清单：哪些文件必须迁移，哪些文件只是参考，哪些文件不要复制。
- 每条链路的最小验收命令：build、flash、monitor、TCP 20 件、日志 audit、真实传感器观察点。
- 依赖和 sdkconfig 的处理原则：什么时候必须回退，什么时候可以升级，升级要保留哪些证据。
- 失败案例索引：模型加载崩溃、串口错误、revision 不匹配、超时时间过短、SPIFFS 文件名过长、RGB/BGR 颠倒。
- 面向 `teammatesproject_old` 的具体移植顺序：先电机还是先视觉，先模拟还是先真实硬件，哪些接口先打桩。

## 当前默认判断

如果后续目标工程和 `merge` 相似，默认采用以下策略：

- 先迁移并跑通电机分拣模拟链路，再接真实硬件输入输出。
- 视觉模型接入先保留最小改动，只替换第二阶段模型或 ROI 输入，不同时重构 UI。
- 模型接入失败时，先记录模型 hash、ESP-DL 版本、输入输出张量和崩溃 PC，再决定是否升级依赖。
- 验证结果要保留日志文件路径、完成分布、audit 结果和关键启动日志，而不是只写“跑通了”。
